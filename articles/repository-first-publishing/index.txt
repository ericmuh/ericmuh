12:Tc6c,<p>This site treats articles as part of the codebase. The writing, images, and publishing configuration live together, so every change is reviewable and versioned.</p>
<h2>One source of truth</h2>
<p>An article is a Markdown file inside <code>content/articles/</code>. Its filename becomes its URL. A file called <code>repository-first-publishing.md</code> lives at <code>/articles/repository-first-publishing/</code>.</p>
<p>The metadata at the top describes the article. The rest is ordinary Markdown:</p>
<pre><code class="language-yaml"><span class="hljs-attr">title:</span> <span class="hljs-string">&quot;A clear title&quot;</span>
<span class="hljs-attr">date:</span> <span class="hljs-string">&quot;2026-10-11&quot;</span>
<span class="hljs-attr">description:</span> <span class="hljs-string">&quot;A short explanation of what readers will learn.&quot;</span>
<span class="hljs-attr">tags:</span> [<span class="hljs-string">&quot;Engineering&quot;</span>]
<span class="hljs-attr">cover:</span> <span class="hljs-string">&quot;/images/articles/my-cover.webp&quot;</span>
<span class="hljs-attr">coverAlt:</span> <span class="hljs-string">&quot;A description of the cover image&quot;</span>
<span class="hljs-attr">draft:</span> <span class="hljs-literal">false</span>
</code></pre>
<p>Images live in <code>public/images/</code>. A local image can be embedded like this:</p>
<pre><code class="language-markdown">![<span class="hljs-string">Describe the image</span>](<span class="hljs-link">/images/articles/my-diagram.webp</span>)
</code></pre>
<h2>Discovery happens during the build</h2>
<p>Next.js reads the article directory, validates metadata and images, and generates a page for each published article. No manual import or registration is necessary.</p>
<p>The output is static HTML, CSS, and JavaScript in <code>out/</code>. The Markdown parser and filesystem access stay in the build environment; the hosting server serves finished files.</p>
<h2>A push and a deployment are different steps</h2>
<p>Pushing an article saves it to GitHub. Updating the live website also requires a successful build and a configured deployment.</p>
<p>The GitHub build workflow checks the content and produces a downloadable website artifact. The separate Hostinger workflow can publish that output once the hosting environment and credentials are configured.</p>
<blockquote>
<p>GitHub is the source of truth. Hostinger serves the built website.</p>
</blockquote>
<h2>Keep drafts explicit</h2>
<p>Use <code>draft: true</code> while an article is unfinished. Drafts are validated but excluded from the website and its generated routes. They remain visible in a public GitHub repository, so this setting is an editorial tool, not a privacy control.</p>
<h2>Why this approach fits</h2>
<p>For public writing on a personal portfolio, a repository-first workflow keeps infrastructure small. There is no content database to operate, no admin panel to secure, and no separate asset store to maintain.</p>
<p>The tradeoff is straightforward: publishing requires a build. For a site updated through a code editor and Git, that is a useful constraint rather than another system to manage.</p>
